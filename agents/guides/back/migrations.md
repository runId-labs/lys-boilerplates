# Migrations (back)

Alembic, managed from `api/` (the worker shares the database). Never
`Base.metadata.create_all` — every schema change is a migration file.

## Commands (in the api container: `docker compose exec api …`)

| Action | Command |
|--------|---------|
| Generate after entity changes | `python main.py makemigrations -m "add product table"` |
| Apply pending | `python main.py migrate` |
| Current revision | `python main.py db-status` |
| Stamp existing DB without running | `python main.py db-stamp` |

Migration files: `api/migrations/versions/` — generated by autogenerate from
the registered entities (which is why entities must be imported through the
app registry: autogenerate walks `Base.metadata` populated by loading apps).

## RULES

- **R1 — Always review the generated file.** Autogenerate misses: PostgreSQL
  enums, column defaults applied client-side, data backfills, index
  renames (it drops+creates). Fix the migration BEFORE applying.
- **R2 — A migration that touches data of a live table must be
  backwards-compatible** with the previous code version during deploy
  (add-then-remove in two migrations when changing a column type).
- **R3 — Migrations are the API's.** Only the api generates/applies them; the
  worker never runs migrations in its boot command (it shares the DB the api
  migrated).
- **R4 — After entity + migration + deploy**: the api container applies pending
  migrations at startup (`CMD` runs `migrate` before the server).
- **R5 — Never edit an applied migration** — append a new one instead.

## PROCEDURE

1. Change `entities.py` (see `entity.md`).
2. `python main.py makemigrations -m "describe the change"` — review the file
   (R1): table names singular, `Uuid(as_uuid=False)` columns become
   `sa.Uuid(as_uuid=False)`, indexes present.
3. `python main.py migrate` → verify with `db-status`.
4. If fixtures seed the new table, check they are env-gated correctly
   (dev/demo only — see lys fixtures semantics in `architecture.md`).
5. Self-check: verification.md B3, B4.
